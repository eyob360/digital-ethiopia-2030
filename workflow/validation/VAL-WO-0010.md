## Failures

1. **Once-per-KPI fallback guard defeated by app-error items (executed: S8).** `Store Observation` (and `Store Raw Document`) use `onError: continueRegularOutput`; when the app endpoint fails persistently (5xx/timeout after the node's 5 retries), the emitted item is `{"error": …}` — carrying neither `status` nor `fallbackUsed`. With the migrated IFs, that item routes `Observation Accepted?` → false, `More Priority URLs?` → false, and `Fallback Already Used?` → **false on every lap** (`$json.fallbackUsed === true` is false when the field is absent) → `Mark Fallback Used` re-runs and the entire fallback pipeline (OpenAI query gen, Tavily, fetch, store) repeats. Observed: 70 iterations in one branch, terminated only by accidental paired-item degradation, not by the guard. In production the loop is usually broken by side channels — the raw-documents `duplicate`/`budget_exhausted` echoes carry `fallbackUsed: true` — but if the app's ingestion endpoints are the failing component (the exact case `onError` exists for), no echo ever restores the flag and the loop is unbounded while OpenAI/Tavily keep billing. This violates the WO's in-scope guarantee "fallback still runs at most once per KPI". This loop is newly reachable via WO-0010's rejected→fallback wiring (on `main`, `Observation Accepted?`'s false path did not exist). Fix options for the next session: route store-node error outputs to `Complete Pipeline Run` via `onError: continueErrorOutput` + an explicit error lane (an app failure cannot be cured by more fallback searching), or normalize items after the store nodes so `fallbackUsed` is rehydrated from lineage (`contextFrom`-style) *before* `Fallback Already Used?` evaluates. Extend the export tests to pin whichever contract is chosen.

## Drift observed

Reported, not fixed, per core rule 5 — all pre-existing on `main`, none introduced by WO-0010:

1. **`Fetch Priority URL` never yields `$json.body` (executed: Probe P, S9) — real-runtime ingestion is inert.** The node declares typeVersion 4.2 but uses the typeVersion-1 parameter `responseFormat: "string"`, which 2.33.0 ignores: JSON responses replace the item with the parsed object; HTML lands in `$json.data`. `Extract Readable Text` reads `$json.body`, so every real fetched page becomes `no-readable-text` — no document is ever stored from any source, and every KPI branch degenerates to fallback-then-complete without ingesting anything. Same defect class as round 2's IF finding (typeVersion-1 parameters under a higher typeVersion node), same node family, present since WO-0006 (`00422f1`). Does not block WO-0010's ACs (routing reachability, which holds, and which S9 shows behaves correctly even for unreadable content), but it refutes WO-0006's runtime ingestion objective — recommend a dedicated fix WO (use the v4 response options or read `$json.data ?? $json.body`), plus an export-test guard for stale parameters generally.
2. **Multi-KPI batch collapses to the first KPI (executed: Probe M).** `Priority URLs First` (and the other single-item `return [{…$json…}]` Code nodes) run in default "Run Once for All Items" mode, so an N-KPI batch from `Expand KPI Batch` collapses to one item — every KPI after the first is silently dropped each run. Identical code on `main`; out of WO-0010's scope (its ACs are per-branch and were validated on the surviving branch). Recommend a fix WO (`mode: runOnceForEachItem` or mapping over all input items).
